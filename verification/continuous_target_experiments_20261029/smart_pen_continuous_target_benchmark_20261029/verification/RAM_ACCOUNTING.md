# RAM accounting — link evidence, not runtime peak

- One heap allocation of **31,104 B** for `pen_continuous_workspace`, containing the **21,888 B** old-core workspace + **9,216 B** crop. The frozen core uses `&ws->core` and the wrapper uses `ws` sequentially. **There are not two concurrently allocated workspaces.**
- One heap allocation of **40,000 B** for the same full-frame input, shared by both decoders. Input + workspace = **71,104 B**, excluding RTOS/libc/static/stack costs.
- Six immutable packed-RLE arrays total **125,442 B** ([('packed_0', 14616), ('packed_1', 19308), ('packed_2', 22920), ('packed_3', 19197), ('packed_4', 21315), ('packed_5', 28086)]). In PURE_RAM, these `const` fixtures reside in **internal DRAM**, not external Flash. Header/name strings, pointers, other constants and alignment add overhead beyond these arrays.
- Main task configured **16,384 B** stack, plus other IDF/RTOS task stacks. Target compiler `.su` reports main/app_main **528 B**, wrapper **416 B**, transform search **464 B**, per-candidate **288 B** and frozen decoder **368 B**; these are individual static frames, not full call-chain/runtime peaks. See compiler-stack-usage.txt.
- Final enabled ELF `size`: text **131,442 B**, data **158,933 B**, bss-labelled **117,864 B**. These aggregate all code including both decoder implementations and full printf/snprintf/dtoa. The bss-labelled figure includes linker alias/dummy reservation; do NOT add it naively to the other figures to claim physical peak. See sections-enabled.txt.
- Full newlib formatting is deliberately linked into internal instruction RAM. `_vfprintf_r`, `_dtoa_r`, `snprintf` and their support code cost code/static resources included above, and may use additional stack/heap while formatting. No claim of separately measured printf heap/stack peak is made. The old nano build size is not an apples-to-apples resource comparator because fixtures/code differ and its64-bit formatting was unsupported.
- image_info reports a **290,480 B** load image, DRAM/IRAM + small RTC segment. Link fit is **not** proof that the71,104 B pair of heap allocations will succeed on a real boot, nor that stack margin is sufficient.
- Either allocation failing prints `fatal` and frees any partial allocation. No decode samples are run then. The strict parser requires every expected sample and memory record in order; a fatal/partial log yields no accepted partial throughput summary. Runtime heap/stack and actual initialized memory require user-approved physical execution and full serial capture, which have NOT happened.
