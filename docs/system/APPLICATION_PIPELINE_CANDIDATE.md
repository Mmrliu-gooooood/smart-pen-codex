# 应用协调管线候选：可执行逻辑，不是已点亮的整笔固件

## 本次实际增加

`firmware/application/pipeline.c` 将已有真实 C 模块串接：调用者提供 Gray8 帧 → 有界工作区、每帧冷搜索解码 → **独立笔尖姿态/标定回调** → 接触/抬笔/图像失效状态机 → Flash 存储抽象 → 精确记录重放/ACK。不是把解码窗口原点直接当笔尖，不使用较弱的 warm-start 局部唯一性假设。约22KiB工作区由调用者提供，非默认任务栈；帧率、堆栈峰值、功耗均未实测。

新 `application_idf` 是独立应用候选，未改原 `runtime_idf` 编译夹具。它包含有序事件、持久 session、待传记录、接触动作、发送与 ACK 协调循环。**默认禁止执行板级提供者，仓库内提供者恒为 NULL**：无摄像头、无 GPIO 动作、无 BLE 建链、无 Flash/NVS 写入、无 OTA。默认或 enabled-compile 构建都不会凭空获得驱动。此应用无 OTA 功能；原 OTA 安装开关未开启，未生成密钥、未烧 eFuse、未刷机。

## 当前不能声称完成的部分

- SC035HGS DVP 初始化、有效数据位、时钟/电平/实际 FPC 映射、DMA 队列与缓存同步仍未验证，未实现真实摄像头提供者。
- 没有镜头/笔芯轴/纸面姿态的 C 实测映射器。接口回调必须真正解算物理笔尖，当前没有可用生产实现。
- 没有 GPIO ISR、相机电源/补光/唤醒实际适配，没有 NimBLE/GATT 服务、配对策略或无线实测。
- 没有批准的最终板号、Flash 分区烧录配置、实际 ESP32 性能、掉电、电池或整笔书写测试。
- 新代码不是任何硬件制造、接电或充电的许可。

## 帧与事件合同

1. 一个 actor 串行拥有管线和存储，禁止 ISR 内解码、写 Flash、调用 BLE 或重入。每个帧工作区只允许单使用者。
2. 一帧包含原始 Gray8 字节、真实捕获时间、严格递增 frame_id、source_id 和明确来源。真实来源标记必须来自捕获驱动，不能由无线数据或测试文件自行授予。
3. 当前同步协调器要求帧时间等于该事件时间；过期/乱序/重复帧不能沿用旧有效坐标。异步传感器需另行实现有序事件队列，排空旧事件后才允许注入当前时间的 idle poll。
4. 每次压力边沿以及无图期间也必须 poll。缺图超过配置窗口会向现有接触状态机报告失效，打断连续笔画；不得插值补造 VALID。
5. 模拟/未知来源、相机未资格化、未知标定、解码失败或映射不一致，永远不产生新的有效坐标。失败图像仍作为无效观察进入接触逻辑，恢复后有 GAP。
6. 映射结果须绑定本帧时间/ID、源 ID、标定版本、纸页、置信度及物理坐标范围。`pose_valid` 只由真正独立映射器确认，不应照抄“解码成功”。元数据校验不是标定或来源的密码学证明。
7. `decoded`/`window` 仅诊断信息。`tip_accepted` 表示映射合同通过，不代表已完成落笔去抖/持久写入或已经发出墨迹。
8. `paper` 与 `page` 当前固定，mapper 必须返回配置页；没有自动跨页识别、热换页配置或多页会话，未知/其他页必须拒绝。
9. 配置中的时间阈值/坐标边界由已验证项目配置提供，本候选不把任意演示参数当成量产默认值。

## 持久与链路边界

- 继续调用现有 `pen_recorder` / `pen_store`，不修改掉电日志、erase intent、session、序号及精确 ACK 规则。未持久的观察不进入重放。
- `pen_app_offer` 只提供当前真实持久记录。发送函数接受/忙都不表示 ACK，不推进/擦除记录。只有成功向指定连接提交整包后才建立应用层 ACK ticket；首次发送忙和单纯查询待传状态均不能授权 ACK。返回1可表示无记录或发送暂忙，调用者稍后重试。
- ACK 同时要求当前连接和**接收瞬间**连接均加密、认证、已绑定且属于批准对端，连接 epoch 非零且相同。epoch 和安全状态来自可信 BLE 栈/策略，不来自 ACK 包。连接epoch须跨重连及设备重启均不复用（须真实provider的持久分配或经验证随机标识策略）；本项目尚未实现/实证跨重启BLE唯一性。每个 ACK 和发送前重查连接状态；发送回调接收 expected_connection_epoch，必须原子检查与排队。连接/批准策略事件仍须由真实适配器串行化，本仓库尚未实现和证明 BLE 原子性。重连后旧队列 ACK 不会借新连接的权限删除记录。
- 这仍是 transport adapter 边界，并未实现 BLE 栈。底层回调须拒绝畸形线协议、保证帧分片和连接事件串行化。旧 `storage_idf` 的20B ACK/3×20B分片可作格式参考，但没有本次发送票据/receipt epoch合同；新提供者不得直接调用旧 `pen_storage_idf_ack` 或底层 store ACK 绕过应用门，只提交解析结果与可信元数据。
- 若提供者不存在，先阻止执行，再接触存储；真实提供者接入时需显式开启两个编译门，并通过分区、板级与物理验证。`pen_storage_idf_open` 可能恢复此前持久的擦除意图，因此不能把启用分支描述成只读。
- `pen_app_pending` 以只读影子 store 查询耐久待传，不改变真实 offer/ACK 状态。它只供状态显示，**不再作为阻止睡眠的 busy 标志**。同步 recorder 每次返回前完成其提交；`pending_transactions` 回调只报告另外真实未提交写入/事务，不能把 Flash backlog 算成 dirty。
- 空闲时发起有界传输收尾，停止接受/撤销在途发送与 ACK 队列，而非等待全部离线记录送达。收尾中再次落笔/拿起会取消收尾；超时或错误进入 safe_stop。提供者给出有依据的 `max_sleep_quiesce_us`，本项目没有量产默认时间。
- `pen_app_prepare_sleep` 要求接触机已进入无接触/无IRQ/无缓冲的睡眠状态、无未提交事务、传输已静默，再执行真实日志同步屏障。成功后保留所有未ACK记录，撤销发送 ticket 与当前 offer、停止 session，进入 sleep_prepared；step/offer/ack 均不再接受，直到重新打开存储并开始新 session。同步失败绝不返回可睡。
- 最终 `apply_actions(SLEEP)` 仍须由真实板级提供者原子重查压力/IRQ、武装兼容唤醒源、停止摄像头/DMA、处理竞态。这里仅定义合同，没有证明硬件原子性。深睡成功通常不返回；若返回/被拒绝，actor 受控停机并要求新 session，不沿用旧 epoch。旧记录重放并不重新授予旧连接 ACK 权限。
- 相机超时、压力/IRQ卡死、时钟故障，以及存储/ACK回调 fatal 错误都会停止 actor、调用 safe_stop。默认 NULL 提供者没有任何硬件动作。

## 容量与持续记录的明确限制

当前仍使用原有**只追加、全分区回收**存储，但应用新增保守维护路径：

- 启动已满槽或已有32个有记录会话时，不盲目 begin 新会话，而进入 `replay_only`。运行中只有明确 append=-2 容量满且日志无故障才进入此模式；CRC/I/O/输入错误不会被清零伪装成容量问题。
- 满时必须 `stop_capture`（相机/LED停止但保留重放链路），`report_status` 对外报告容量错误、槽数/会话数和禁止记录状态。只重放已持久记录，不继续输出未存轨迹。真实灯/UI/BLE仍需提供者实现。
- 当前压力/IRQ释放、无未提交事务、没有剩余未ACK记录时，进行跨poll有界传输静默；最终 `maintenance_idle_guard` 原子检查实际压力/IRQ及待处理帧/边沿/事务，维护期间保持采集禁止，后续边沿排队，不可丢弃。发生竞态取消维护。
- 同步屏障、撤销旧发送票据/offer、停止记录后，调用原有 `pen_store_reclaim`；它再次扫描全日志确认每条耐久ACK，使用持久erase intent保护整区擦除。未ACK不覆盖。擦除中断后只能经原 open 恢复，不能把fault位清零继续。
- 回收后经 `pen_storage_idf_begin_boot` **先提交递增NVS epoch**再开始新session，旧session/seq与ACK不能复用。32会话限制现在有明确回收路径；32个未ACK会话必须先补传，不能强开第33个。
- 普通空闲睡眠只在已满槽/32会话门槛且全ACK时回收，非每次抬笔擦区。长时间保持落笔时没有滚动扇区回收，满后仍需抬笔、补传和维护，不能声称无限无间断书写。
- 容量满但离线时同样可在空闲超时、真实事务完成、传输静默及日志sync后休眠，保留全部记录；醒后先进入只读补传，再决定维护。睡眠撤销ticket，旧连接不能授权新ACK。
- 回收前必须报告 `actor_error=-109` 与 `recording=false`（维护忙）；3.875MiB全日志扫描/整区擦除是同步阻塞，不能声称拿起即写。guard后的新压力只排队，维护期间不接收轨迹、不生成VALID；真实最长耗时未知。不能抢占已经开始的同步Flash调用，超时返回后safe_stop/重启，不把超时当成功。
- 维护/睡眠deadline在回调之后及提交动作之前复查；超时不会被迟到的quiet成功绕过。真实Flash擦除耗时/电源安全窗口尚需测量与设置合适上限。

每条记录固定64字节：48字节packet、8字节ACK body、4字节ACK提交标记、4字节记录提交标记；session/seq标识已含在48字节packet内，没有额外session专用槽；NVS epoch/擦除意图在另一个NVS分区。容量 C 提供 floor(C/64) 槽。当前默认官方SDK分区仅NVS24KiB、PHY4KiB、factory1MiB，**没有 pen_records，实际可用日志为0**；不能用整颗Flash容量冒充日志容量。

下表只给指定日志容量的数学上界，不是实测帧率/续航：

| 日志容量 | 槽数 | 60记录/s上界 | 120记录/s上界 |
|---|---:|---:|---:|
| 默认未配置 |0|0|0|
| 512KiB示例 |8192|136.53s|68.27s|
| 可选8MiB profile净日志3.875MiB |63488|1058.13s|529.07s|
| 8MiB整区（仅对比，不是实际分区） |131072|2184.53s|1092.27s|

边沿/GAP等会消耗额外记录；例如**仅在额外事件≤2条/s且预留10槽**的假设下，512KiB约131.97s@60Hz /67.07s@120Hz。事件率无上限就不能保证该范围；插入帧丢失/GAP以及反复重启会降低容量。4小时×60×64需要55,296,000字节（约52.7MiB），未计额外边沿/GAP记录及另置NVS分区，不能用4小时电池目标推断离线容量。可选8MiB profile净日志0x3E0000=4,063,232字节、63488槽；上述同一额外2条/s及10槽假设下约1023.84s@60Hz /520.31s@120Hz。profile保留双2MiB OTA槽但没有OTA执行器。运行时须实际JEDEC物理容量与镜像逻辑容量均为8MiB，并精确匹配全部分区/当前OTA槽；默认profile关闭或16MiB DevKit均拒绝。不得把PICO N8R8与DevKit N16R8混同；须实物确认再考虑烧录。

## 验证与再现

`tests/test_application_pipeline.py` 编译真实 C 管线，使用原有生成器的完整像素图，不给解码器答案。测试为覆盖有条件成功分支，明确用测试捕获替身标记 SENSOR；这不提供任何真实相机资格证据。测试中的映射器是**显式测试替身**，返回与窗口原点无关的固定坐标，只验证协调合同，不是物理标定。它覆盖模拟帧/未知来源/未资格化、10类映射拒绝、重复帧、短图像、缺帧 GAP、恢复、抬笔、发送忙、精确 ACK、旧连接/未认证 ACK 和写入故障。

另有 `test_application_actor.py` 编译真实 app_main 并模拟窄 IDF/板级接口，验证默认关闭、无提供者、ACK fatal 和相机/接触/IRQ/时钟故障均不继续运行/发送；还覆盖离线待传可睡、真实 dirty 延期、静默超时/失败、同步失败和新落笔取消收尾。还覆盖迟到quiet/sync不得睡、满日志离线可睡、运行中满后只读补传→新epoch恢复、32会话启动恢复、异步维护静默与超时、最终维护guard竞态/失败。`test_application_maintenance.py` 验证未ACK拒绝回收、32已ACK回收、掉电erase intent恢复、睡醒补传和旧ACK隔离。模拟不是设备实测。
