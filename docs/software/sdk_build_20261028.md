# 2026-10-28 SDK compile/link gate — not a flashable pen release

`firmware/runtime_idf` is a **compile/link harness** for the new persistent-store,
contact/prewake, recorder and update/recovery adapters. `app_main()` always prints
one no-hardware-actions warning and returns. It never initializes storage, erases
flash/NVS, starts OTA, requests reboot, changes GPIO, powers a camera or sleeps.
Both build configurations retain this behavior.

The main component explicitly requires the real `storage` and `update` components,
compiles `runtime/contact_power.c` and `runtime/recorder.c`, and forces all fourteen
public adapter/state-machine APIs into the final ELF using linker undefined-symbol
retention. This avoids an apparent successful build whose adapter code was removed
as unused. Vendor libraries and headers are used, not the host-test API mocks.

## Pinned build inputs
- Official Espressif ESP-IDF tag `v5.4`, commit
  `67c1de1eebe095d554d281952fde63c16ee2dca0`, official pinned submodules.
- Xtensa GCC `14.2.0` / `esp-14.2.0_20241119`; target `esp32s3`.
- SDK-created Python `3.12.14` environment; separately installed into that same
  isolated workspace environment: CMake `3.31.10`, Ninja `1.13.0`.
- SDK/tools/build trees are sibling `smart_pen_sdk_20261028/`, not committed into
  the source repository. No global Python packages, user credentials or hardware
  state were modified by these builds.
- Harness `PROJECT_VER="1"` is a **compile fixture**, exercising the strict signed
  `app_desc.version` integer policy. The test board/project identifier is
  `smartpen_runtime_compile`, not a physical board qualification.

This pin is a reproducibility target, not a recommendation to deploy an old SDK
release without security-advisory and supported-patch review.

## Configurations
1. Default: flash recording and OTA installation opt-ins disabled.
2. `sdkconfig.enabled_compile.defaults`: flash recording opt-in and OTA install
   opt-in enabled at **compile time**, rollback enabled, signed-on-update software
   verification enabled through official Kconfig. Hardware Secure Boot and eFuse
   anti-rollback remain disabled. The SDK remote-signing flow has
   `SECURE_BOOT_BUILD_SIGNED_BINARIES=n`: **the output app is unsigned and cannot be
   installed by this signature-enforcing OTA path**. No private/public signing
   key was generated, supplied, copied or committed.

The generated enabled sdkconfig must show `CONFIG_SECURE_SIGNED_ON_UPDATE=y` as a
real Kconfig-derived option, not a compiler macro override. Project and hardware
identifiers must match the signed app-description identity. No update can actually
begin from this harness because its main never calls an adapter.

The default SDK partition table here is only a compiler fixture. It does not
provision approved dual OTA slots, the `pen_records` raw partition, reserved NVS
capacity or production flash geometry. An integration build with those approved
layouts and real runtime authorization remains a separate gate. Do not flash the
harness or use it as a production release binary.

## Reproduce (build only)
After cloning the official SDK and running its `install.sh esp32s3` with an explicit
workspace `IDF_TOOLS_PATH`, install CMake/Ninja only in that SDK Python environment:
```bash
export SDK=/absolute/path/smart_pen_sdk_20261028
export IDF_TOOLS_PATH="$SDK/tools"
. "$SDK/esp-idf/export.sh"
export PATH="$IDF_TOOLS_PATH/python_env/idf5.4_py3.12_env/bin:$PATH"
python -m pip install cmake==3.31.10 ninja==1.13.0
cd /absolute/path/smart_pen_firmware_next_20261028/firmware/runtime_idf
idf.py -B "$SDK/build-runtime-disabled" \
  -D SDKCONFIG="$SDK/runtime-disabled.config" -D IDF_TARGET=esp32s3 \
  -D CMAKE_MAKE_PROGRAM="$IDF_TOOLS_PATH/python_env/idf5.4_py3.12_env/bin/ninja" build
idf.py -B "$SDK/build-runtime-enabled" \
  -D SDKCONFIG="$SDK/runtime-enabled.config" \
  -D SDKCONFIG_DEFAULTS="$PWD/sdkconfig.enabled_compile.defaults" \
  -D IDF_TARGET=esp32s3 \
  -D CMAKE_MAKE_PROGRAM="$IDF_TOOLS_PATH/python_env/idf5.4_py3.12_env/bin/ninja" build
```
Use fresh external config/build paths when reproducing changed defaults. Existing
sdkconfig values override defaults; do not quietly assume a defaults-file edit
changed a previously generated configuration. SDK logs print suggested flash
commands automatically; **none were executed**.

## Outcome
Both final configurations **passed real vendor compile/link** after the recorder and
strict `app_desc.version` policy changes. No compiler warning/error was found in
these final build logs. The enabled SDK log explicitly says **App built but not
signed**.

Final binary sizes, SHA-256 and source bindings are kept only in
[`compile_report.json`](../../firmware/runtime_idf/compile_report.json), the single
source of final build evidence. This final rebuild includes the first44-byte ACK
binding fix and recorder input-error fault latch.

`esptool image_info --version 2` independently reports project
`smartpen_runtime_compile`, App version `1`, Secure version `0`, ESP-IDF `v5.4`.
The enabled generated config has actual `PEN_FLASH_RECORDING=y`,
`PEN_OTA_ALLOW_INSTALL=y`, `SECURE_SIGNED_ON_UPDATE=y`,
`BOOTLOADER_APP_ROLLBACK_ENABLE=y`, and identical project/hardware identifiers.
`BOOTLOADER_APP_ANTI_ROLLBACK`, `SECURE_BOOT` and local signed-binary generation are
disabled. The standard SDK flash geometry shown by image_info is only a compile
fixture, not a board flash-capacity selection.

`xtensa-esp-elf-nm` confirms fourteen retained public APIs in **both** ELFs: contact
init/step, recorder init/step, five storage APIs and five update APIs. Machine-readable
sizes, hashes, symbols, configuration facts and SHA-256 of the compiled source
files are in `firmware/runtime_idf/compile_report.json`. Final logs are sibling
`smart_pen_sdk_20261028/build-runtime-disabled.log` and
`smart_pen_sdk_20261028/build-runtime-enabled.log`; binaries/build trees stay out
of the source repository. Build paths/timestamps can change binary hashes on a
rebuild; the report binds this particular execution.

Host/state-machine simulation evidence remains separately documented. Compilation
is not evidence of physical power-cut recovery, battery safety, radio
interoperability or handwriting accuracy. SC035HGS DVP/close-focus/pose decoding
is still unqualified.
